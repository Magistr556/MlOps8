# Контрольные вопросы по лабораторным работам

## Лабораторная работа №1. Воспроизводимый проект: данные и пайплайн

### 1. Что фиксирует uv.lock и почему его недостаточно для воспроизводимости ML-проекта?
Файл uv.lock фиксирует точные версии всех зависимостей проекта, включая транзитивные зависимости. Это позволяет устанавливать одинаковое программное окружение на разных компьютерах.
Для полной воспроизводимости ML-проекта этого недостаточно, поскольку uv.lock не фиксирует версии датасетов, параметры эксперимента, состояние обученной модели и последовательность обработки данных. 
Для этого используются дополнительные инструменты, например Git, DVC и файл params.yaml.

### 2. Что хранится в Git, что в хранилище DVC и как они связаны между собой?
В Git хранятся:
- исходный код программы;
- конфигурационные файлы;
- параметры экспериментов;
- метафайлы DVC (.dvc).
В удалённом хранилище DVC (DagsHub Storage) находятся сами файлы данных и другие отслеживаемые DVC артефакты.

Связь обеспечивается через метафайлы DVC, которые содержат информацию о соответствующих версиях файлов и их контрольных хешах.
Git фиксирует состояние проекта, а DVC позволяет восстановить необходимые версии данных и результатов.

### 3. Как DVC определяет, какие этапы пайплайна нужно пересчитать?
DVC анализирует зависимости каждого этапа пайплайна, указанные в dvc.yaml.

Он проверяет:
- изменения исходного кода;
- изменения входных данных;
- изменения параметров в params.yaml;
- изменения зависимостей между этапами;
- наличие и состояние выходных файлов.
Для этого DVC использует контрольные хеши. Если входные данные, параметры и код не изменились, этап повторно не выполняется. 
Если изменения обнаружены, DVC пересчитывает соответствующий этап и зависимые от него последующие этапы.

### 4. Почему ключи доступа задаются с флагом --local, а адрес хранилища — без него?
Флаг --local используется для сохранения конфиденциальных данных, например ключей доступа, в локальном файле .dvc/config.local, который не должен попадать в Git.
Адрес удалённого хранилища не является секретной информацией, поэтому его сохраняют в общей конфигурации .dvc/config. 
Она может быть добавлена в Git, чтобы другие пользователи получили настройки подключения к хранилищу без необходимости самостоятельно указывать его адрес.
Конфигурация проекта доступна всем участникам, а секретные ключи остаются только на локальной машине.

### 5. Почему dvc push выполняется раньше git push?
Команда dvc push отправляет данные и артефакты в удалённое DVC-хранилище, а git push отправляет в GitHub код, конфигурации и метафайлы DVC.
Сначала необходимо загрузить сами данные, чтобы к моменту публикации Git-коммита соответствующие объекты уже существовали в удалённом хранилище.
Если выполнить git push раньше dvc push, другие пользователи могут получить ссылку на версию данных, которая ещё не была загружена в DVC Storage.

### 6. Какие две команды возвращают проект к состоянию месячной давности вместе с данными?
git checkout <commit or tag>
dvc checkout

Первая команда переключает Git на нужную версию проекта, восстанавливая соответствующий исходный код и конфигурацию.
Вторая команда восстанавливает версии данных и DVC-артефактов, соответствующие выбранному

### 7. Почему случайное разбиение данных с датой завышает оценку качества?
При работе с временными данными случайное разбиение на обучающую и тестовую выборки может привести к утечке информации из будущего в прошлое.
Например, модель может обучаться на наблюдениях за декабрь, а проверяться на наблюдениях за октябрь. 
В реальных условиях модель не имела бы доступа к будущим данным, поэтому такая проверка не отражает реальные условия эксплуатации.
Это приводит к завышенной оценке качества модели и неправильному представлению о её способности прогнозировать будущие значения.
Для временных данных следует использовать хронологическое разделение: более ранние наблюдения идут в обучающую выборку, а более поздние — в тестовую.
